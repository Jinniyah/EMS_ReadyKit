## Context

EMS ReadyKit manages **mission-critical operational metadata** for a Fire & EMS organization, including:
- Vehicle readiness checks
- Inventory state and movements
- Expiration management
- Controlled substance accountability

While the system does **not** process patient or PHI data, it operates in a domain where:
- Audits are expected
- Accountability matters
- Certain actions (e.g., controlled substance discrepancies) must be highly visible

The project must demonstrate:
- Centralized, queryable logs
- Clear separation between application logs and audit events
- Operationally meaningful alerting
- Cost discipline appropriate to a non-production system

---

## Decision

Adopt a **centralized logging and audit strategy** using **Azure Log Analytics** as the system of record for:

- Platform telemetry
- Application logs
- Explicit audit events

Selected high-signal events may be forwarded to an **optional SIEM (Security Onion)** to validate security detection and correlation workflows.

All logging infrastructure is deployed and configured via **Terraform**.

---

## Logging Architecture

### Central Log Store
- One Azure Log Analytics Workspace
- Receives logs from:
  - Application runtime
  - Application-generated audit events
  - Azure platform diagnostics (where applicable)

### Log Types

#### Application Logs
Used for:
- Debugging
- Operational health
- Workflow visibility

Examples:
- API request failures
- Inventory update operations
- Daily check submissions

Characteristics:
- Informational
- Time-limited retention
- Not treated as authoritative audit records

---

#### Audit Events
Used for:
- Accountability
- Compliance modeling
- Security correlation

Audit events are **explicitly generated by the application** and include:
- Actor (user identity)
- Action performed
- Entity type and identifier
- Timestamp
- Contextual metadata (station, vehicle, item, lot)

Audit events are treated as **first-class signals**, not derived logs.

---

## High-Sensitivity Events

The following events are explicitly elevated in severity:

- Controlled substance discrepancies
- Unauthorized access attempts
- Cross-station access violations
- Inventory quantity anomalies

These events may:
- Trigger alerts within Log Analytics
- Be forwarded to Security Onion for correlation
- Be preserved longer than routine logs (within cost constraints)

---

## Authorization & Data Scope in Logs

All application-generated logs and audit events include:
- `station_id`
- `vehicle_id` (where applicable)

This enables:
- Station-level filtering
- Vehicle-centric investigations
- Correlation of repeated anomalies over time

Log consumers are restricted via RBAC to prevent cross-station visibility where inappropriate.

---

## SIEM Integration (Optional)

### Purpose
Security Onion is used to:
- Validate detection capability
- Demonstrate correlation use cases
- Reinforce security observability skills

### Scope
- Selected high-signal logs only
- No full log firehose
- Explicitly cost-controlled

Security Onion is considered:
- A demonstration and validation tool
- Not a production SOC replacement

---

## Alternatives Considered

### Distributed or Per-Resource Logging
**Rejected**

Scattered logs:
- Increase investigation time
- Reduce audit defensibility
- Obscure system-wide patterns

Centralization provides clear operational signal.

---

### Database-Derived Auditing Only
**Rejected**

Relying solely on database state:
- Loses actor intent
- Complicates investigations
- Weakens compliance posture

Explicit audit event generation preserves context.

---

### Managed SIEM (Azure Sentinel)
**Rejected**

Managed SIEM services:
- Increase cost significantly
- Hide detection detail
- Reduce hands-on validation

Security Onion provides transparency appropriate for this project.

---

## Consequences

### Positive
- Clear audit trail for all material actions
- Strong alignment with real EMS accountability expectations
- Low-cost observability
- Demonstrable detection and investigation workflows
- IaC-enforced consistency

### Tradeoffs
- Limited log retention by design
- Detection quality depends on selected signals
- System is not certified for regulatory compliance

These tradeoffs are intentional and documented.

---

## Rationale

This logging and audit strategy:
- Emphasizes **signal over noise**
- Separates operational logging from audit accountability
- Aligns with real-world public-sector practices
- Demonstrates security and observability maturity without excess cost

By treating audit events as **domain primitives**, the system remains defensible under review and realistic in operation.

## Implementation Notes (updated 2026-05-15)

### Request correlation ID
A `request_id` (UUID) is generated per request by the logging middleware in
`main.py` and injected into every log line via the `_EmsJsonFormatter` in
`core/logging.py`. This allows grouping all log output for one API call in
Log Analytics using KQL:

```kql
AppServiceConsoleLogs
| extend log = parse_json(ResultDescription)
| where log.request_id == "a3f2c1d4-..."
| order by TimeGenerated asc
```

The `X-Request-ID` header is also returned in every API response, allowing
the frontend to include it in bug reports and feedback submissions.

### Request-level logging middleware
Added to `main.py` — logs method, path, status_code, duration_ms, and
client_ip for every request except health check and docs paths. Requests
returning 4xx or 5xx are logged at WARNING level; 2xx/3xx at INFO.
This provides the operational baseline for endpoint performance monitoring
and error spike detection without SQL-level verbosity.

### Structured extra fields convention
All application log calls that include `extra={}` must use these field names
consistently to ensure KQL queries work reliably:
  action, entity_type, entity_id, severity, actor,
  vehicle_id, station_id, request_id, duration_ms, status_code

### Log volume estimate
At 200 API calls/day (typical for one station, one shift):
- Request logs: ~200 lines/day × ~500 bytes = ~100KB/day
- Audit events (DB): ~50 rows/day × ~300 bytes = ~15KB/day
- Log Analytics ingestion: ~3MB/month — well within free tier (5GB/month)
